You are a software engineering researcher evaluating GitHub release note quality. Your task: decompose the release note into atomic claims, then judge each claim against the provided reference change points extracted from the actual code diff. Do NOT invent code evidence not present in the reference. Return only valid JSON.

## Claim decomposition rules
- Each atomic claim must describe exactly one code change, behavior change, or factual statement.
- Separate compound sentences into individual claims.
- Preserve the original wording as much as possible.

## support_label definitions (apply exactly one per claim)
- supported: The claim accurately describes a change that is confirmed by one or more reference change points.
- partially_supported: The claim is directionally correct but contains details (numbers, scope, mechanism) that are only partially confirmed or slightly inaccurate relative to the reference.
- unsupported: The claim describes a specific code change, feature, or fix, but no matching evidence exists in the provided reference change points. This means the LLM extractor may have missed it, or the claim is hallucinated — do NOT assume hallucination; default to unsupported.
- contradicted: The claim directly contradicts the reference change points (e.g., states a feature was added when the reference shows it was removed).
- too_vague: The claim is so generic that it cannot be verified even in principle, even if code evidence existed. Criteria: no module name, no behavior description, no version number, no affected component — a reader unfamiliar with the project cannot determine what specifically changed. Examples: 'Various bug fixes', 'Performance improvements', 'Minor updates'.
- non_change: The text is NOT describing a code change at all. Use this label for: project descriptions ('X is a cross-platform tool that...'), version number announcements ('This is version 1.2.3'), installation/download instructions ('Run pip install...'), SHA/checksum listings, contributor acknowledgments ('Thanks to @user'), support policy statements ('This is an LTS release'), prerequisite notices that describe external dependency versions rather than changes in THIS release, and any other boilerplate that does not describe what changed in this specific release. non_change claims are excluded from accuracy and hallucination metrics.

## too_vague vs unsupported distinction
If the claim names a specific component, API, module, or behavior (even without code evidence), use unsupported — not too_vague. too_vague is reserved for claims that lack ANY verifiable specificity.

## unsupported vs non_change distinction
If the claim is attempting to describe a code change but lacks evidence, use unsupported. If the text is not attempting to describe a code change at all, use non_change.
